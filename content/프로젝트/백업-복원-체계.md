**기간** 2026.10.20 ~ 10.22 · **역할** 설계·구축·복원 시험 단독

> **기여도 100%** — 설계·구축·복원 시험 전부 본인. 7월에 만든 이전 백업 설계 저장소도 커밋 8/8, 변경 3,516줄 전부 본인 작성.

## 배경

이전 백업 체계는 설계만 있고 예약 작업(cron)이 돌지 않았습니다. 통과 기준 10개 중 1개만 충족한 상태였고, GitLab은 수동 백업 한 번, 이슈 관리 도구는 몇 달 전 백업 1건이 전부였습니다.

## 설계

- 백업 서버가 매주 수요일 새벽에 각 서버에서 수집하고, 다른 서버에 사본을 하나 더 둡니다.
- 보관: 최근 4주 + 월별 3개월. 하드링크로 중복 용량을 줄였습니다.
- **수집 계정은 정해진 명령만 실행할 수 있습니다.** 다른 명령을 보내면 거부되는지 서버 8대 모두 시험했습니다.
- DB 접근은 비밀번호 대신 소켓·peer 인증을 씁니다. 설정 파일에 비밀번호가 남지 않게 하기 위함입니다.
- `nice`·`ionice`로 우선순위를 낮춰 업무 시간 서비스에 영향이 없게 했습니다.

## 결과

| 실행 | 결과 |
|---|---|
| 수동 1회 | 13개 파일, 7.2GB, 실패 0, 약 13분 |
| 첫 예약 실행 | 14개 파일, 8.8GB, 검증 14/14, 16분 |

**복원 시험**을 따로 했습니다. 백업은 복원이 되어야 의미가 있어서입니다. 네트워크를 끊은 Podman 컨테이너(`--network none`)에 복원해 운영 서비스와 섞이지 않게 했습니다.

- 제품 DB 7,169,000행 복원 (76초), 원본과 일치
- 이슈 관리 도구 표 62/62, 아티팩트 저장소 132/132 일치
- GitLab 저장소 49개 무결성 검사 통과
- 메신저, Jenkins까지 서비스 5종을 약 20분 안에 복원 확인

## 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 백업 체계가 있는데도 백업이 안 쌓임 | 7월 설계는 검증 단계를 못 넘겨 예약 작업을 켜지 못한 상태 | 범위를 줄여 다시 설계하고, 첫 예약 실행까지 검증해 가동 |
| 백업 수집 계정이 탈취되면 전 서버가 위험 | 수집용 계정에 셸 권한이 있으면 다른 명령도 실행 가능 | 계정별로 정해진 명령만 실행되게 제한, 8대 모두 거부 시험 |
| 복원 시험이 운영 서비스와 섞일 위험 | 복원한 서비스가 운영 DB·외부로 접속할 수 있음 | 네트워크 없는 Podman 컨테이너에서 복원 |
| 일일 백업 하루치 누락 | 타이머를 `enable`만 하고 `start` 안 함 | 아래 참고 |

## 배운 점

일일 백업 타이머 하나를 `systemctl enable`만 하고 `start`를 빠뜨려 하루치가 비었습니다. 다음 날 점검에서 발견해 바로잡았고, 이후로는 타이머를 등록하면 `systemctl list-timers`로 다음 실행 시각이 잡혔는지까지 확인합니다.
