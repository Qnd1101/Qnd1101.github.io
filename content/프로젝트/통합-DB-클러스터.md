## 배경

사내 DB가 앱 서버마다 흩어져 있었고, 정기 백업은 사실상 없었습니다. 가장 중요한 제품 DB(5.4GB)는 서버 한 대에만 있고 백업도 없었습니다. 서버 10대를 실측(9월, 10월 두 차례)해 현황을 정리하고, DB를 전용 클러스터로 모으는 계획을 세웠습니다.

## 기술 선택: 왜 Patroni인가

문서마다 "수동 승격"안과 "Pacemaker + PAF"안이 섞여 있어서 비교한 뒤 Patroni로 정했습니다.

- Patroni는 etcd 과반 합의, 자기 강등, watchdog으로 split-brain(두 서버가 동시에 주가 되는 상황)을 막습니다. 앞선 2노드 이중화에서 fencing이 실패했던 유형을 피할 수 있습니다.
- PAF는 2020년 이후 새 릴리스가 없습니다.

구성은 PostgreSQL 17 + Patroni 4.1 + etcd 3.7, 서버 3대입니다. 비동기 복제를 쓰고, 하드웨어 watchdog과 etcd 인증을 켰습니다.

## 결과

0.5초마다 한 행씩 쓰는 부하를 걸어 놓고 장애를 만들었습니다.

| 시험 | 쓰기 중단 | 손실 |
|---|---|---|
| 주 DB 프로세스 강제 종료 | 약 25초 | 0 |
| 주 DB 네트워크 고립 | 약 27초 | 3행 |
| etcd 1대 정지 | 0초 | 0 |
| 수동 전환 왕복 | 약 1초 | 0 |

네트워크 고립 시 3행 손실은 비동기 복제의 특성(고립 직후 약 7초 분량)입니다. 이 수치를 그대로 기록하고, 손실을 허용할 수 없는 DB에는 동기 복제를 검토하도록 남겼습니다.

첫 이관 대상 서비스 DB는 **정지 약 43초**로 옮겼고, 표 41개의 행 수(합계 2,134)가 모두 일치했습니다. 구 DB는 바로 지우지 않고 읽기 전용으로 남겨 두었습니다.

## 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 문서마다 이중화 방식이 달라 진행 불가 | 수동 승격안과 Pacemaker+PAF안이 섞여 있었음 | 장애 유형·유지보수 상태로 비교해 Patroni로 단일화 |
| 네트워크 고립 시험에서 3행 손실 | 비동기 복제라 고립 직후 약 7초 분량이 대기 서버로 못 감 | 수치를 그대로 기록하고, 손실 불가 DB는 동기 복제 검토로 분리 |
| 첫 DB 이관 시도 중단 | 같은 시각 다른 작업 세션이 해당 서비스를 배포 중 | 즉시 멈추고 배포 종료 후 재시도 → 정지 43초로 완료 |

## 진행 상황

나머지 DB 이관과 watchdog 방식 확정은 진행 중입니다.
